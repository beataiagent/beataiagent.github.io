3.2 Multi-agent workflow patterns: Sequential, Parallel, Loop, and dynamic routing

The Rosku Bank orchestration failures: race conditions and infinite loops!

Rosku Bank’s lending team builds a multi-agent commercial loan pipeline in ADK, and three orchestration bugs hit immediately:

  1. In their ParallelAgent credit check, all three concurrent sub-agents (Equifax, TransUnion, and OFAC) write their results to output_key="check_result"—overwriting each other’s data in session.state!
  2. In their LoopAgent compliance drafter, the Critic Agent outputs the text "APPROVED - STOP LOOP" when the draft passes, but the LoopAgent ignores the text and keeps looping until max_iterations is exhausted!
  3. When the root Triage Agent delegates a small math lookup to a sub-agent via sub_agents, the sub-agent takes over the whole user conversation instead of returning the math result back to the Triage Agent!
Module 3.2 in a nutshell
  • Deterministic workflow agents (no LLM routing overhead): Use SequentialAgent for fixed step-by-step chains, ParallelAgent for concurrent fan-out (where every branch must write to a unique output_key to prevent race-condition overwrites!), and LoopAgent for iterative Generator-Critic cycles (which stop only when a tool/agent sets EventActions(escalate=True) or hits max_iterations).
  • sub_agents transfer vs. AgentTool: Attaching specialists via sub_agents=[…] hands conversation control over to the child agent (transfer_to_agent); wrapping a specialist in AgentTool(agent=…) calls the child like a function tool and returns the answer back to the parent agent!
  • Imperative Python branching: Subclass BaseAgent (CustomAgent) and override _run_async_impl(ctx) whenever you need deterministic Python if/else branching across sub-agents based on session.state.

1. Key concept definitions: the 6 ADK orchestration primitives

ADK separates deterministic workflow agents (which execute in code without an LLM deciding the control flow) from dynamic LLM routing and custom imperative agents:

1. SequentialAgent
Strict chronological pipeline
  • What it is: Executes its sub_agents list in strict order (Step 1 → Step 2 → Step 3).
  • Why you need it: Passes the exact same InvocationContext and session.state along the chain so Step 2 can read Step 1’s output_key deterministically.
2. ParallelAgent
Concurrent fan-out + unique keys
  • What it is: Executes independent sub_agents concurrently to slash latency.
  • Why you need it: Because all branches share the same session.state, each branch must use a unique output_key to avoid race-condition overwrites!
3. LoopAgent and escalate=True
Iterative cycle + exit signal
  • What it is: Repeatedly runs its sub_agents in sequence for iterative refinement (Drafter + Critic).
  • Why you need it: Loops until either max_iterations is reached OR a sub-agent/tool emits an Event with EventActions(escalate=True).
4. Dynamic sub_agents transfer
transfer_to_agent(agent_name=…)
  • What it is: Attaching children to an LlmAgent(sub_agents=[…]) for dynamic LLM-driven routing.
  • Why you need it: The parent LLM reads each child’s description and calls transfer_to_agent—handing conversation control over to the target specialist.
5. AgentTool (Agent-as-a-Tool)
tools=[AgentTool(agent=…)]
  • What it is: Wraps a specialist agent inside AgentTool(agent=…) and passes it in the parent’s tools=[…] list.
  • Why you need it: The specialist runs in an isolated sub-invocation and returns its answer back to the parent agent, which keeps control of the user chat!
6. CustomAgent (BaseAgent)
Subclass BaseAgent + _run_async_impl
  • What it is: Subclasses BaseAgent and overrides _run_async_impl(ctx) in Python.
  • Why you need it: Lets you write arbitrary imperative Python control flow (such as if/else branching on ctx.session.state) between child agents.

3. Master multi-agent orchestration matrix

Compare the six ADK orchestration mechanisms across control flow, state sharing, and primary architectural triggers:

Orchestration pattern Who controls the flow? How state and outputs flow Primary architectural trigger
SequentialAgent Deterministic code (Fixed order: A -> B -> C) Shares InvocationContext; Step A writes output_key="k1", Step B reads {k1}. Multi-stage pipelines where every step must run in a guaranteed order.
ParallelAgent Deterministic code (All branches run concurrently) Shares session.state concurrently; every branch needs a unique output_key. Running independent lookups (Credit + Fraud + Income) simultaneously to cut latency.
LoopAgent Deterministic code (Repeats sub_agents in a cycle) Iterates until max_iterations OR a sub-agent/tool emits EventActions(escalate=True). Generator + Critic refinement loops or iterative self-correction until a rubric passes.
LlmAgent(sub_agents=[...]) Dynamic LLM reasoning (transfer_to_agent) Parent LLM reads child description fields and hands conversation control to the selected child. Triage/concierge routers dispatching unpredictably structured user requests to domain bots.
AgentTool(agent=...) Dynamic LLM reasoning (Parent calls child as a tool) Child runs in an isolated sub-invocation and returns its result back to the parent agent. Parent must consult multiple specialists and synthesize the final answer itself (or wrap a built-in Search agent).
CustomAgent (BaseAgent) Imperative Python code (_run_async_impl) Full programmatic inspection of ctx.session.state with Python if/else branching across child agents. Complex conditional workflows where branch selection depends on deterministic Python rules rather than LLM choice.

4. Real-world deep dive: workflow agent brain-twisters

Architect question How it works under the hood in production
“In a LoopAgent, why doesn’t the loop stop when the Critic Agent outputs the text 'APPROVED'—and how does tool_context.actions.escalate = True stop it?”
  • Deterministic event signal vs. free text: LoopAgent does not use an LLM to read its sub-agents’ text outputs!
  • Instead, after each sub-agent finishes, LoopAgent checks the emitted ADK Event.actions.escalate boolean flag. Give the Critic Agent a simple exit_loop(tool_context: ToolContext) function tool that sets tool_context.actions.escalate = True when the draft passes!
“Can we nest Workflow Agents inside each other—for example, putting a ParallelAgent and a LoopAgent inside a parent SequentialAgent?”
  • 100% composable hierarchy (BaseAgent): Because SequentialAgent, ParallelAgent, LoopAgent, and LlmAgent all inherit from BaseAgent, you can nest them arbitrarily!
  • A classic production blueprint is SequentialAgent([ParallelAgent([Credit, Fraud]), SynthesizerAgent, LoopAgent([Drafter, ComplianceCritic])]).
“When should we subclass BaseAgent (CustomAgent) instead of using SequentialAgent or LlmAgent(sub_agents=[...])?”
  • Deterministic conditional branching (if/else): SequentialAgent always runs every sub-agent in its list, while LlmAgent relies on probabilistic LLM routing.
  • If you need deterministic conditional logic—such as “Run HighRiskAuditAgent ONLY if ctx.session.state[‘loan_amount’] > 500000, otherwise skip directly to FastApprovalAgent”—subclass BaseAgent and write a standard Python if/else block inside _run_async_impl(ctx)!

Golden rules for Module 3.2

  1. Known fixed sequence = SequentialAgent. Independent concurrent lookups = ParallelAgent (with unique output_keys!).
  2. Iterative Generator-Critic cycle = LoopAgent terminated via EventActions(escalate=True) + max_iterations.
  3. Hand off the chat = sub_agents. Call a specialist and keep control in the parent = AgentTool!
