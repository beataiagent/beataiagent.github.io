4.1 Agent evaluation: trajectory modes, rubric syntax, and autoraters

The Rosku Bank pre-launch failure: right answer, wrong path!

Before launching Rosku Bank’s Mortgage Underwriting Agent to production, the QA team tests it using simple final-text string matching (response_match_score). The tests pass—but in staging, three critical flaws appear:

  1. The agent approves a loan by guessing the customer’s credit score instead of calling verify_identity() before check_credit_score()!
  2. When a ParallelAgent runs check_fraud() and check_income() concurrently, the evaluation suite randomly fails whenever check_income() finishes first!
  3. When evaluating open-ended financial explanations, lexical ROUGE matching (response_match_score) marks valid answers as failures just because the wording changed slightly!
Module 4.1 in a nutshell
  • Grade the path (trajectory), not just the final text: Use tool_trajectory_avg_score (ToolTrajectoryCriterion) with EXACT for strict step-by-step compliance, IN_ORDER when extra helper tools are allowed between required steps, and ANY_ORDER when a ParallelAgent runs tools concurrently!
  • Stop false negatives on open-ended answers: Replace rigid word-overlap matching (response_match_score) with semantic LLM judging (final_response_match_v2 when you have a reference answer) or custom domain rubrics (rubric_based_final_response_quality_v1 and rubric_based_tool_use_quality_v1).
  • Single-agent scoring vs. head-to-head A/B comparison: In the Vertex AI Evaluation SDK (EvalTask), use PointwiseMetric (or dynamic RubricBasedMetric) to score one agent on a scale, and use PairwiseMetric to compare Candidate v2 against Baseline v1 side-by-side!

1. Key concept definitions: the agent evaluation stack

Evaluating an autonomous agent requires grading both the intermediate path (trajectory) and the final output (response and rubrics) across five core building blocks:

1. EvalSet and EvalCase
*.evalset.json
  • What it is: ADK’s golden test dataset format storing multi-turn Invocation objects.
  • Why you need it: Records user_content, expected intermediate_data.tool_uses (tool names + arguments), and reference final_response for repeatable regression testing.
2. ToolTrajectoryCriterion
EXACT | IN_ORDER | ANY_ORDER
  • What it is: Configures tool_trajectory_avg_score inside test_config.json to verify tool call sequences.
  • Why you need it: Lets you choose EXACT (strict 1-to-1), IN_ORDER (allows extra helper tools), or ANY_ORDER (for concurrent parallel tool calls).
3. ADK RubricBasedCriterion
RubricContent(text_property=…)
  • What it is: Powers rubric_based_final_response_quality_v1 and rubric_based_tool_use_quality_v1 using an LLM autorater.
  • Why you need it: Grades custom pass/fail domain rules (like required APR disclosures or search query scoping) without needing a fixed reference string.
4. PointwiseMetric & RubricBasedMetric
EvalTask single-agent scoring
  • What it is: Platform Evaluation SDK classes passed into EvalTask.evaluate().
  • Why you need it: Scores a single agent’s output against static criteria (PointwiseMetricPromptTemplate) or dynamically generated per-prompt rubrics (RubricBasedMetric).
5. PairwiseMetric (A/B autorater)
Baseline v1 vs. Candidate v2
  • What it is: Side-by-side LLM judge using PairwiseMetricPromptTemplate.
  • Why you need it: Compares a Candidate Agent (v2) directly against a Baseline Agent (v1) to compute Win/Loss/Tie percentages before promoting v2.

4. Real-world deep dive: trajectory and rubric brain-twisters

Architect question How it works under the hood in production
“Because LLM agents are non-deterministic, a single test run might pass by luck. How does ADK handle run-to-run variance during evaluation?”
  • Multi-run averaging (num_runs): In AgentEvaluator.evaluate(…, num_runs=3), ADK executes each EvalCase multiple times and averages the resulting trajectory and rubric scores before comparing against the threshold in test_config.json!
“When should I use final_response_match_v2 vs. rubric_based_final_response_quality_v1?”
  • Reference text vs. rule checklist: Use final_response_match_v2 when your EvalCase has a specific target answer (“The wire fee is $25”) and you want to allow synonyms (“It costs twenty-five dollars”).
  • Use rubric_based_final_response_quality_v1 when the output is open-ended (e.g., a personalized retirement plan) and you need to verify compliance rules (“Includes APR disclaimer” and “Uses empathetic tone”).
“What happens if an agent calls [check_credit, verify_id] when the golden trajectory is [verify_id, check_credit]?”
  • EXACT fails, IN_ORDER fails, ANY_ORDER passes! Both EXACT and IN_ORDER require verify_id to happen chronologically before check_credit. Only ANY_ORDER ignores sequence order!

Golden rules for Module 4.1

  1. Parallel tool calls failing trajectory tests randomly? Switch tool_trajectory_avg_score to ANY_ORDER.
  2. Valid answers failing response_match_score due to phrasing? Upgrade to final_response_match_v2 (if you have a reference answer) or rubric_based_final_response_quality_v1 / PointwiseMetric (for custom rubric criteria)!
  3. Comparing Agent v1 vs. Agent v2 head-to-head? Use PairwiseMetric inside EvalTask.evaluate()!

4.2 Deployment runtimes: Agent Runtime, Cloud Run, and GKE Agent Sandbox

The Rosku Bank hosting dilemma: 3 agents, 3 different infrastructure needs!

Rosku Bank’s platform architects must deploy three very different AI agents into production:

  1. The Retail Loan Orchestrator: Built in Python ADK. The team wants zero Dockerfile or Kubernetes overhead and wants managed SessionService and Memory Bank wired up automatically out of the box.
  2. The Spiky Tax-Season Bot: Packaged as a custom container alongside a lightweight Node.js PDF parser. Traffic is zero at night and spikes to 5,000 concurrent users at 9:00 AM—requiring fast serverless scale-to-zero!
  3. The Quant Code-Execution Agent: Executes untrusted, user-submitted Python and C++ quantitative models and requires dedicated GPU node pools plus strict kernel-level sandbox isolation (gVisor / microVMs) so malicious code can never escape the container!
Module 4.2 in a nutshell
  • Turnkey zero-Dockerfile hosting: Pick Managed Agent Runtime (wrapping your agent in AdkApp) when you want the lowest operational overhead with auto-wired managed Sessions, Memory Bank, Managed Agent Identity, and Cloud Trace.
  • Custom containers and scale-to-zero: Pick Serverless Cloud Run when you need custom OS binaries or polyglot sidecars, fast scale-to-zero during idle hours, and high async I/O concurrency—and always externalize session state (never use InMemorySessionService across multiple instances!).
  • Untrusted code execution and custom GPUs/TPUs: Pick GKE with Agent Sandbox when running untrusted user/AI code inside per-execution kernel boundaries (gVisor / Kata microVMs with pre-warmed sandbox pools) or hosting open-weight models on custom GPU/TPU node pools.

1. Key concept definitions: the 3 production agent runtimes

Select your Google Cloud hosting target based on operational overhead, state integration, and isolation requirements:

1. Managed Agent Runtime
AdkApp (zero Dockerfile)
  • What it is: The turnkey managed runtime on the Gemini Enterprise Agent Platform.

gVisor / microVMs + GPU/TPU pools
  • What it is: Kubernetes cluster hosting paired with per-execution kernel sandboxing on GKE.
  • Why you need it: Provides custom GPU/TPU node pools (for self-hosted open models) and strict kernel isolation (gVisor / Kata microVMs + pre-warmed pools) for running untrusted code safely.

4. Real-world deep dive: stateful scaling and sandbox mechanics

Architect question How it works under the hood in production
“Why does enabling load-balancer sticky sessions (session affinity) fail to fix InMemorySessionService state loss on Cloud Run or GKE?”
  • Containers are ephemeral! Session affinity only attempts to route a user to the same container while that container stays alive.
  • As soon as Cloud Run scales down an idle instance, crashes, or rolls out a new deployment revision, everything in local container RAM (InMemorySessionService) is wiped permanently. Always externalize state to managed VertexAiSessionService or DatabaseSessionService (Cloud SQL / AlloyDB / Spanner)!
“Why should Cloud Run container concurrency be set higher than 1 for most ADK agents?”
  • Agents are network I/O-bound, not CPU-bound! An ADK agent spends over 90% of its turn waiting on network responses from the Gemini API and remote MCP tools.
  • Using async def tools and allowing a single container to handle 50–80 concurrent requests slashes compute costs and avoids cold-start storms!
“How does GKE Agent Sandbox execute untrusted code in milliseconds without cold-booting a VM every time?”
  • Pre-warmed sandbox pools and snapshot restore: GKE maintains a warm pool of pre-initialized gVisor/microVM sandbox pods.
  • When an agent tool call arrives, it attaches to a warm sandbox in milliseconds, runs the untrusted binary in an isolated kernel/filesystem, and destroys/resets the snapshot immediately afterward!

Golden rules for Module 4.2

  1. Zero-ops ADK hosting + built-in Sessions and Memory Bank = Agent Runtime.
  2. Custom containers + scale-to-zero cost savings = Cloud Run (always pair with an external persistent SessionService!).
  3. Executing untrusted code/binaries in isolated kernel sandboxes or custom GPU node pools = GKE with Agent Sandbox!

4.3 Agent Starter Pack, CI/CD evaluation gates, and safe rollouts

The Rosku Bank release disaster: Friday afternoon deployment crash!

Rosku Bank’s loan engineering team manually deploys Version 2.0 of their Mortgage Underwriting Agent on a Friday afternoon:

  1. Because they wired up cloud permissions by hand in the console instead of using standardized templates, the Staging environment works but Production fails with missing IAM bindings!
  2. A subtle system-prompt edit breaks the agent’s tool calling sequence, but the CI pipeline only ran Python syntax lint checks (flake8) instead of an automated trajectory evaluation gate!
  3. Switching 100% of live traffic immediately to Version 2.0 changes the session.state key format mid-conversation, crashing 400 active customer mortgage applications!
Module 4.3 in a nutshell
  • Bootstrap production repos in one command: Use the Google Cloud Agent Starter Pack (agent-starter-pack) to scaffold multi-environment Terraform IaC (Dev/Staging/Prod), automated RAG ingestion pipelines, CI/CD evaluation gates, and OpenTelemetry + BigQuery observability sinks.
  • Prompts are executable control flow: Version prompts, model IDs, and tool schemas in Git alongside code, and run AgentEvaluator.evaluate() in CI/CD (fast trajectory smoke tests on Pull Requests + full golden EvalSet and rubric autoraters in Staging).
  • Safe stateful rollouts: Use session-pinned canary routing (pinning active session_id chats to v1 while routing 5%–10% of new chats to v2), Blue/Green cutovers for instant 1-click rollback, and shadow (dark launch) mode with all mutating/write tools mocked!

1. Key concept definitions: the AgentOps and release stack

Moving an agent from prototype to production relies on five core release engineering building blocks:

1. Agent Starter Pack
Terraform + CI/CD + RAG + Telemetry
  • What it is: Google Cloud’s official production accelerator (agent-starter-pack) for ADK agents.
  • Why you need it: Scaffolds a complete repository with multi-environment Terraform IaC, CI/CD pipelines, RAG data ingestion, evaluation harnesses, and OpenTelemetry + BigQuery sinks.
2. CI/CD evaluation gate
AgentEvaluator.evaluate() in CI
  • What it is: An automated test stage in Cloud Build or GitHub Actions triggered on code or prompt changes.
  • Why you need it: Halts deployment (non-zero exit code) whenever trajectory or rubric scores drop below test_config.json thresholds.
3. Session-pinned canary
Pinned by session_id
  • What it is: Gradual traffic shifting (5% → 25% → 100%) using consistent hashing or header routing on session_id.
  • Why you need it: Routes a small slice of brand-new sessions to Agent v2 while keeping existing in-flight session_id conversations on Agent v1 so state schemas never break mid-chat.
4. Blue/Green deployment
Instant cutover + warm standby
  • What it is: Brings the new revision (Green) up alongside the stable revision (Blue) and switches router traffic cleanly once verified.
  • Why you need it: Keeps Blue warm so active sessions drain gracefully and rollback takes a single click if telemetry alerts fire.
5. Shadow (dark launch) mode
Async mirror + mocked write tools
  • What it is: Mirrors live production requests asynchronously to Agent v2 in the background while only v1’s reply is shown to the user.
  • Why you need it: Evaluates real-world performance with zero user impact—provided all mutating/write tools are mocked so v2 never executes duplicate transactions!

4. Real-world deep dive: stateful rollout and shadow tool-mocking mechanics

Architect question How it works under the hood in production
“How does an API gateway or load balancer actually pin an active conversation to v1 during a canary rollout while routing 10% of new conversations to v2?”
  • Consistent hashing / header-based routing on session_id: When a brand-new conversation starts, the gateway assigns it to v1 (90%) or v2 (10%) and tags the session metadata (or sets a signed routing cookie/header).
  • On Turns 2 through 10, the gateway inspects the session_id routing tag and deterministically forwards the request to the exact revision where Turn 1 started!
“In shadow (dark launch) mode, how do we prevent the shadow v2 agent from executing duplicate wire transfers without rewriting the agent’s Python tool code?”
  • Environment-scoped MCP server / callback interception: Point the shadow v2 deployment’s MCP Toolbox configuration (tools.yaml) at a read-only/sandboxed mock endpoint, OR attach an environment-aware before_tool_callback (if ENV == ‘SHADOW’ and tool.is_mutating: return {‘status’: ‘mocked_success’}) so write calls are short-circuited safely!
“Why do prompt edits require the exact same CI/CD evaluation gate as Python code changes?”
  • Prompts are executable control flow! Changing three words in an LlmAgent instruction or tool description can alter which sub-agent gets selected or skip a compliance check—even though flake8 and standard unit tests pass 100%.
  • Running AgentEvaluator.evaluate() in CI/CD catches behavioral drift before deployment.

Golden rules for Module 4.3

  1. Standardize IaC, CI/CD, RAG ingestion, and telemetry fast = Agent Starter Pack.
  2. Prevent bad prompt edits from reaching Prod = automated CI/CD evaluation gate (AgentEvaluator.evaluate()).
  3. Canary rollouts for multi-turn agents = pin routing by session_id. Shadow testing = mock all mutating tools!

4.4 OpenTelemetry tracing, Cloud Monitoring, and cost/latency optimization

The Rosku Bank production mystery: the 18-second latency spike!

Two weeks after launching Rosku Bank’s Multi-Agent Wealth Platform, customers complain that responses intermittently take 18 seconds, and the monthly Gemini token bill has tripled!

  1. Because the system has 1 Coordinator Agent, 4 Sub-Agents, and 12 MCP tools, looking at flat text logs in Cloud Logging makes it impossible to tell which hop caused the 18-second delay!
  2. When an external credit-score API returns HTTP 429 (Rate Limit Exceeded), the agent enters a retry spiral instead of failing gracefully!
  3. The team wants to harvest production conversations where users clicked “Thumbs Down” and turn them into new golden evalset.json regression cases automatically!
Module 4.4 in a nutshell
  • Pinpoint multi-agent latency bottlenecks: Use Cloud Trace with nested OpenTelemetry spans (invocation → agent_run → call_llm → execute_tool) and propagate the W3C traceparent HTTP header across remote A2A and MCP hops so distributed calls stitch into one unified waterfall!
  • Build the production evaluation flywheel: Route structured JSON logs via a Cloud Logging sink to BigQuery, run asynchronous LLM autoraters offline on a 1%–5% sample (zero added user latency!), and harvest “Thumbs Down” traces into your CI/CD *.evalset.json.
  • Slash latency and survive HTTP 429 spikes: Tier simple routing to Gemini Flash, set include_contents=‘none’ on stateless worker sub-agents, enable Context Caching, retry transient errors with exponential backoff + random jitter, and reserve Provisioned Throughput for predictable mission-critical peaks!

1. Key concept definitions: the observability and optimization stack

1. Cloud Trace and OpenTelemetry
invocation → call_llm → execute_tool
  • What it is: Visualizes a multi-agent turn as a hierarchical waterfall of nested OpenTelemetry spans.
  • Why you need it: Isolates exact latency bottlenecks (TTFT vs. tool wait time) and input/output token counts per hop across sub-agents.
2. W3C traceparent propagation
traceparent: 00-trace_id-span_id-01
  • What it is: Standard HTTP context header injected into outbound remote A2A and MCP calls.
  • Why you need it: Stitches child spans from remote microservices directly under the parent orchestrator’s trace ID in Cloud Trace.
3. BigQuery telemetry flywheel
Cloud Logging sink → BigQuery
  • What it is: Streams structured JSON agent logs (with trace_id, trajectories, and user feedback) into BigQuery tables.
  • Why you need it: Powers offline autorater sampling (5% live traffic) and automatic harvesting of failed turns into golden *.evalset.json test cases.
4. Provisioned Throughput & jitter
Guaranteed capacity + backoff
  • Provisioned Throughput: Reserves dedicated model capacity on the Gemini Enterprise Agent Platform to prevent HTTP 429 quota errors during predictable peaks.
  • Exponential backoff + jitter: Adds random millisecond delays to retries to prevent “thundering herd” collisions on spiky bursts.

4. Real-world deep dive: distributed tracing and online autorater mechanics

Architect question How it works under the hood in production
“When an ADK orchestrator on Agent Runtime calls a remote A2A agent on Cloud Run, why do they show up as two separate, unlinked traces unless we configure context propagation?”
  • Stitching distributed spans via W3C traceparent: Each service generates its own root trace_id unless the caller passes its active OpenTelemetry context in the outbound HTTP header (traceparent: 00-<trace_id>-<span_id>-01).
  • When the remote A2A or MCP server reads that header, it attaches its child spans directly under the orchestrator’s parent span in Cloud Trace!
“Why shouldn’t we run RubricBasedMetric or hallucinations_v1 LLM autoraters inline before returning every production chat response?”
  • Inline autoraters double latency and token cost! Calling an LLM judge takes 1–3 seconds and extra tokens.
  • Unless a domain requires synchronous blocking (where lightweight deterministic callbacks or Model Armor are preferred), evaluate production quality asynchronously by sampling 5% of BigQuery logs offline!
“Why do we add ‘jitter’ (random millisecond delay) to exponential backoff when retrying HTTP 429 errors?”
  • Preventing thundering herd collisions: If 500 concurrent agent turns hit an HTTP 429 quota limit at t=0 and all retry at exact intervals (1.0s, 2.0s, 4.0s), all 500 requests will collide again at the exact same millisecond!
  • Adding random jitter spreads the retries smoothly across time.

Golden rules for Module 4.4

  1. Debug multi-agent latency hops = Cloud Trace (OpenTelemetry spans + W3C traceparent).
  2. Analyze long-term trends and harvest golden evalsets = Cloud Logging sink to BigQuery.
  3. Guarantee capacity for predictable mission-critical peaks = Provisioned Throughput!

rubric_based_final_response_quality_v1 (ADK criterion key) RubricBasedCriterion(threshold=0.8, judge_model_options=JudgeModelOptions(...), rubrics=[Rubric(rubric_id="...", rubric_content=RubricContent(text_property="..."))]) Uses an LLM autorater to grade the agent’s final response against custom pass/fail domain rules (text_property), averaging scores across rubrics. rubric_based_tool_use_quality_v1 (ADK criterion key) RubricBasedCriterion(threshold=1.0, judge_model_options=..., rubrics=[Rubric(rubric_id="...", rubric_content=RubricContent(text_property="..."))]) Uses an LLM autorater to grade intermediate tool selection and parameter quality against natural-language rules. Dynamic tool calls (e.g., generated SQL or search queries) where exact string matching in tool_trajectory_avg_score is too brittle.
tool_trajectory_avg_score (ADK criterion key) ToolTrajectoryCriterion(threshold=1.0, match_type=MatchType.EXACT | MatchType.IN_ORDER | MatchType.ANY_ORDER) Deterministically compares actual intermediate_data.tool_uses (tool name + args) against the golden EvalCase. Verifying deterministic tool sequences (EXACT), prerequisite order (IN_ORDER), or concurrent parallel calls (ANY_ORDER).

Upgrade from response_match_score to final_response_match_v2 when valid answers fail due to synonyms or paraphrasing!
hallucinations_v1 & safety_v1 (ADK criterion keys) LlmAsAJudgeCriterion(threshold=1.0, evaluate_intermediate_nl_responses=True) hallucinations_v1 verifies that every factual claim in the response is strictly supported by retrieved context/tool outputs. Preventing ungrounded fabrications in financial, medical, or legal RAG agents.
PointwiseMetric & PointwiseMetricPromptTemplate (Platform Eval SDK) PointwiseMetric(metric="custom_name", metric_prompt_template=PointwiseMetricPromptTemplate(criteria={"rule1": "..."}, rating_rubric={"1": "Pass", "0": "Fail"}, input_variables=[...])) Evaluates a single model/agent output per dataset row against custom criteria and rating_rubric definitions. Custom single-agent rubric scoring inside EvalTask(dataset=df, metrics=[...]).evaluate().
RubricBasedMetric (Platform Eval SDK) RubricBasedMetric(generation_config=RubricGenerationConfig(prompt_template=...), critique_metric=PointwiseMetric(...)) Dynamically generates prompt-specific pass/fail rubrics per test case (or uses predefined rubrics) and critiques the response against each rubric item. Evaluating diverse datasets where each prompt requires its own dynamically tailored checklist of rubrics!
PairwiseMetric & PairwiseMetricPromptTemplate (Platform Eval SDK) PairwiseMetric(metric="v1_vs_v2", baseline_model=baseline_fn, metric_prompt_template=PairwiseMetricPromptTemplate(criteria={...}, rating_rubric={...})) Runs side-by-side (A/B) LLM autorater judging between baseline_model and the candidate model, outputting win/loss/tie rates. Choosing whether Candidate Agent v2 outperforms Baseline Agent v1 before promoting v2 to production!

Golden rules for Section 4

  1. Evaluation: Combine trajectory evaluation (EXACT, IN_ORDER, ANY_ORDER) with rubric and groundedness autoraters (RubricBasedCriterion, hallucinations_v1, PointwiseMetric, PairwiseMetric).
  2. Runtimes & rollouts: Use Agent Runtime for turnkey AdkApp, Cloud Run (+ external SessionService) for scale-to-zero containers, GKE Agent Sandbox for untrusted code, session-pinned canary for stateful rollouts, and mocked write tools in shadow mode.
  3. Observability: Trace hops in Cloud Trace (W3C traceparent), stream logs to BigQuery for async autorater sampling and golden dataset harvesting, and reserve capacity via Provisioned Throughput!
