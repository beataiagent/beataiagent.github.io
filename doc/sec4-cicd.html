4.3 Agent Starter Pack, CI/CD evaluation gates, and safe rollouts

The Rosku Bank release disaster: Friday afternoon deployment crash!

Rosku Bank’s loan engineering team manually deploys Version 2.0 of their Mortgage Underwriting Agent on a Friday afternoon:

  1. Because they wired up cloud permissions by hand in the console instead of using standardized templates, the Staging environment works but Production fails with missing IAM bindings!
  2. A subtle system-prompt edit breaks the agent’s tool calling sequence, but the CI pipeline only ran Python syntax lint checks (flake8) instead of an automated trajectory evaluation gate!
  3. Switching 100% of live traffic immediately to Version 2.0 changes the session.state key format mid-conversation, crashing 400 active customer mortgage applications!
Module 4.3 in a nutshell
  • Bootstrap production repos in one command: Use the Google Cloud Agent Starter Pack (agent-starter-pack) to scaffold multi-environment Terraform IaC (Dev/Staging/Prod), automated RAG ingestion pipelines, CI/CD evaluation gates, and OpenTelemetry + BigQuery observability sinks.
  • Prompts are executable control flow: Version prompts, model IDs, and tool schemas in Git alongside code, and run AgentEvaluator.evaluate() in CI/CD (fast trajectory smoke tests on Pull Requests + full golden EvalSet and rubric autoraters in Staging).
  • Safe stateful rollouts: Use session-pinned canary routing (pinning active session_id chats to v1 while routing 5%–10% of new chats to v2), Blue/Green cutovers for instant 1-click rollback, and shadow (dark launch) mode with all mutating/write tools mocked!

1. Key concept definitions: the AgentOps and release stack

Moving an agent from prototype to production relies on five core release engineering building blocks:

1. Agent Starter Pack
Terraform + CI/CD + RAG + Telemetry
  • What it is: Google Cloud’s official production accelerator (agent-starter-pack) for ADK agents.
  • Why you need it: Scaffolds a complete repository with multi-environment Terraform IaC, CI/CD pipelines, RAG data ingestion, evaluation harnesses, and OpenTelemetry + BigQuery sinks.
2. CI/CD evaluation gate
AgentEvaluator.evaluate() in CI
  • What it is: An automated test stage in Cloud Build or GitHub Actions triggered on code or prompt changes.
  • Why you need it: Halts deployment (non-zero exit code) whenever trajectory or rubric scores drop below test_config.json thresholds.
3. Session-pinned canary
Pinned by session_id
  • What it is: Gradual traffic shifting (5% → 25% → 100%) using consistent hashing or header routing on session_id.
  • Why you need it: Routes a small slice of brand-new sessions to Agent v2 while keeping existing in-flight session_id conversations on Agent v1 so state schemas never break mid-chat.
4. Blue/Green deployment
Instant cutover + warm standby
  • What it is: Brings the new revision (Green) up alongside the stable revision (Blue) and switches router traffic cleanly once verified.
  • Why you need it: Keeps Blue warm so active sessions drain gracefully and rollback takes a single click if telemetry alerts fire.
5. Shadow (dark launch) mode
Async mirror + mocked write tools
  • What it is: Mirrors live production requests asynchronously to Agent v2 in the background while only v1’s reply is shown to the user.
  • Why you need it: Evaluates real-world performance with zero user impact—provided all mutating/write tools are mocked so v2 never executes duplicate transactions!

3. Rollout strategy decision matrix: Canary vs. Blue/Green vs. Shadow vs. A/B

Rollout strategy How traffic is routed Critical agentic constraint Primary architectural use case
Canary deployment Shifts a small slice (e.g., 5% → 25% → 100%) of live requests to v2 while monitoring metrics. Must use session-pinned routing so existing session_id threads don’t flip between v1 and v2 mid-conversation! Gradually validating a new prompt, model version, or toolset in production with minimal blast radius.
Blue/Green deployment Runs full v2 (Green) alongside v1 (Blue) and switches router traffic cleanly once verified. Keep v1 warm so active long-running sessions drain gracefully and rollback takes 1 click. Major architectural upgrades requiring instant cutover and zero-downtime rollback capability.
Shadow / dark launch Mirrors live user requests asynchronously to v2 in the background; only v1’s reply is shown to the user. Must mock/disable mutating tools in the shadow v2 environment so v2 never executes duplicate database writes or payments! Testing a new foundation model (e.g., upgrading to a new Gemini release) on real production traffic with zero user-facing risk.
A/B experimentation Splits cohorts (e.g., 50% Group A / 50% Group B) with sticky user assignment to measure business KPIs. Requires statistical sample sizing and user-level cohort sticky routing (user_id hash). Measuring which agent persona or conversational flow drives higher customer conversion or CSAT scores.

4. Real-world deep dive: stateful rollout and shadow tool-mocking mechanics

Architect question How it works under the hood in production
“How does an API gateway or load balancer actually pin an active conversation to v1 during a canary rollout while routing 10% of new conversations to v2?”
  • Consistent hashing / header-based routing on session_id: When a brand-new conversation starts, the gateway assigns it to v1 (90%) or v2 (10%) and tags the session metadata (or sets a signed routing cookie/header).
  • On Turns 2 through 10, the gateway inspects the session_id routing tag and deterministically forwards the request to the exact revision where Turn 1 started!
“In shadow (dark launch) mode, how do we prevent the shadow v2 agent from executing duplicate wire transfers without rewriting the agent’s Python tool code?”
  • Environment-scoped MCP server / callback interception: Point the shadow v2 deployment’s MCP Toolbox configuration (tools.yaml) at a read-only/sandboxed mock endpoint, OR attach an environment-aware before_tool_callback (if ENV == ‘SHADOW’ and tool.is_mutating: return {‘status’: ‘mocked_success’}) so write calls are short-circuited safely!
“Why do prompt edits require the exact same CI/CD evaluation gate as Python code changes?”
  • Prompts are executable control flow! Changing three words in an LlmAgent instruction or tool description can alter which sub-agent gets selected or skip a compliance check—even though flake8 and standard unit tests pass 100%.
  • Running AgentEvaluator.evaluate() in CI/CD catches behavioral drift before deployment.

Golden rules for Module 4.3

  1. Standardize IaC, CI/CD, RAG ingestion, and telemetry fast = Agent Starter Pack.
  2. Prevent bad prompt edits from reaching Prod = automated CI/CD evaluation gate (AgentEvaluator.evaluate()).
  3. Canary rollouts for multi-turn agents = pin routing by session_id. Shadow testing = mock all mutating tools!
