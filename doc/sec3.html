3.1 Single-agent design, prompting, and ADK parameters

The Rosku Bank design challenge: the confused Loan Intake Agent!

Rosku Bank builds its first Loan Intake Agent using the Agent Development Kit (ADK). Immediately, three things break in testing:

  1. The root coordinator agent keeps routing home-mortgage questions to the Credit Card Agent instead of the Loan Intake Agent!
  2. When the Loan Intake Agent calculates a customer’s Debt-to-Income (DTI) ratio, it replies in free-form paragraphs instead of strict JSON, crashing the downstream underwriting step!
  3. The next agent in the pipeline cannot find the calculated DTI result in session.state, and stateless formatting workers are re-reading 50 turns of prior chat history on every hop!
Module 3.1 in a nutshell
  • description vs. instruction: Parent/coordinator agents read only description to decide which sub-agent gets the task; instruction steers this agent’s own internal reasoning and supports dynamic {state_key} injection (or {state_key?} for optional keys).
  • Never mix tools and output_schema on the same agent: Enabling output_schema (Pydantic BaseModel) forces strict JSON output and disables tool calling on that agent turn. Split into a 2-step sequence: Agent 1 calls tools and saves to output_key; Agent 2 (with include_contents=‘none’) formats into output_schema!
  • Planners and transfer bounds: Use BuiltInPlanner (with Gemini ThinkingConfig) or PlanReActPlanner for step-by-step planning, and set disallow_transfer_to_parent=True / disallow_transfer_to_peers=True so specialist sub-agents don’t hand off prematurely.

1. Key concept definitions: inside an ADK LlmAgent

Before wiring multiple agents together, review the six core configuration primitives of ADK’s fundamental building block—the LlmAgent (also aliased as Agent):

1. description vs. instruction
External route vs. internal brain
  • description: External routing metadata read by parent/coordinator agents to decide task delegation.
  • instruction: Read by this agent’s own LLM to govern its reasoning, persona, and tool use.
2. Dynamic state templates
{var_name} & {var_name?}
  • What it is: Placing {var_name} inside instruction automatically interpolates session.state[‘var_name’] at runtime.
  • Why you need it: Adding a trailing question mark ({var_name?}) safely ignores missing optional keys without throwing an error, or pass a callable InstructionProvider function to skip brace parsing.
3. output_schema vs. output_key
Pydantic JSON vs. state save
  • output_schema: Takes a Pydantic BaseModel to force strict JSON output (which disables tool calls on that same agent turn).
  • output_key: Automatically writes the agent’s final response into session.state[output_key] for downstream agents.
4. include_contents=‘none’
Stateless history pruning
  • What it is: Strips prior conversation history from the model call.
  • Why you need it: Ensures a stateless worker or JSON formatting sub-agent processes only its instruction (including injected {state_key} variables), slashing token bills!
5. Built-in and ReAct planners
BuiltInPlanner & PlanReActPlanner
  • What it is: Reasoning controllers attached via the planner parameter on LlmAgent.
  • Why you need it: BuiltInPlanner (with Gemini ThinkingConfig) or PlanReActPlanner instructs the agent to generate an explicit multi-step plan before calling tools or answering.
6. Model tiering and transfer bounds
Flash/Pro + disallow_transfer
  • Model tiering: Pair Gemini Flash (low-latency routers/formatters) with Gemini Pro (deep reasoning).
  • Transfer bounds: Set disallow_transfer_to_parent=True and disallow_transfer_to_peers=True to prevent premature handoffs.

4. Real-world deep dive: LlmAgent parameter brain-twisters

Architect question How it works under the hood in production
“Why does an LlmAgent configured with BOTH tools=[credit_check] AND output_schema=LoanJSON fail to call its tool, and how do we solve it?”
  • Two-step sequential split: In ADK, setting output_schema constrains the model’s decoding output strictly to that JSON schema, preventing intermediate function-calling turns on that agent.
  • Solve this with a 2-step SequentialAgent: Agent 1 calls credit_check and saves to output_key=“raw_credit”; Agent 2 (with no tools and include_contents=‘none’) reads {raw_credit} and applies output_schema=LoanJSON!
“If we set include_contents='none' on Agent 2 so prior chat history is excluded, how does Agent 2 still receive the data from Agent 1?”
  • State interpolation still runs on instruction! Even when include_contents=‘none’ strips the conversation history list, ADK still resolves {raw_credit} placeholders inside Agent 2’s instruction from session.state[‘raw_credit’]—giving Agent 2 the exact structured input it needs at a fraction of the token cost!
“How do we inject dynamic context into instruction if we do NOT want ADK’s automatic {brace} interpolation to parse literal curly braces (like JSON examples) in our prompt?”
  • Pass a callable InstructionProvider function: Instead of passing a static str to instruction, pass a Python function def build_instruction(ctx: ReadonlyContext) -> str:.
  • When instruction is a callable function, ADK uses your function’s return string verbatim and skips automatic {brace} parsing!

Golden rules for Module 3.1

  1. Parent routing depends on description; internal behavior depends on instruction.
  2. output_key writes to session.state; {key} inside instruction reads from session.state.
  3. Never combine tool calling and output_schema inside the exact same LlmAgent—use a two-step agent handoff instead!

3.2 Multi-agent workflow patterns: Sequential, Parallel, Loop, and dynamic routing

The Rosku Bank orchestration failures: race conditions and infinite loops!

Rosku Bank’s lending team builds a multi-agent commercial loan pipeline in ADK, and three orchestration bugs hit immediately:

  1. In their ParallelAgent credit check, all three concurrent sub-agents (Equifax, TransUnion, and OFAC) write their results to output_key="check_result"—overwriting each other’s data in session.state!
  2. In their LoopAgent compliance drafter, the Critic Agent outputs the text "APPROVED - STOP LOOP" when the draft passes, but the LoopAgent ignores the text and keeps looping until max_iterations is exhausted!
  3. When the root Triage Agent delegates a small math lookup to a sub-agent via sub_agents, the sub-agent takes over the whole user conversation instead of returning the math result back to the Triage Agent!
Module 3.2 in a nutshell
  • Deterministic workflow agents (no LLM routing overhead): Use SequentialAgent for fixed step-by-step chains, ParallelAgent for concurrent fan-out (where every branch must write to a unique output_key to prevent race-condition overwrites!), and LoopAgent for iterative Generator-Critic cycles (which stop only when a tool/agent sets EventActions(escalate=True) or hits max_iterations).
  • sub_agents transfer vs. AgentTool: Attaching specialists via sub_agents=[…] hands conversation control over to the child agent (transfer_to_agent); wrapping a specialist in AgentTool(agent=…) calls the child like a function tool and returns the answer back to the parent agent!
  • Imperative Python branching: Subclass BaseAgent (CustomAgent) and override _run_async_impl(ctx) whenever you need deterministic Python if/else branching across sub-agents based on session.state.

1. Key concept definitions: the 6 ADK orchestration primitives

ADK separates deterministic workflow agents (which execute in code without an LLM deciding the control flow) from dynamic LLM routing and custom imperative agents:

1. SequentialAgent
Strict chronological pipeline
  • What it is: Executes its sub_agents list in strict order (Step 1 → Step 2 → Step 3).
  • Why you need it: Passes the exact same InvocationContext and session.state along the chain so Step 2 can read Step 1’s output_key deterministically.
2. ParallelAgent
Concurrent fan-out + unique keys
  • What it is: Executes independent sub_agents concurrently to slash latency.
  • Why you need it: Because all branches share the same session.state, each branch must use a unique output_key to avoid race-condition overwrites!
3. LoopAgent and escalate=True
Iterative cycle + exit signal
  • What it is: Repeatedly runs its sub_agents in sequence for iterative refinement (Drafter + Critic).
  • Why you need it: Loops until either max_iterations is reached OR a sub-agent/tool emits an Event with EventActions(escalate=True).
4. Dynamic sub_agents transfer
transfer_to_agent(agent_name=…)
  • What it is: Attaching children to an LlmAgent(sub_agents=[…]) for dynamic LLM-driven routing.
  • Why you need it: The parent LLM reads each child’s description and calls transfer_to_agent—handing conversation control over to the target specialist.
5. AgentTool (Agent-as-a-Tool)
tools=[AgentTool(agent=…)]
  • What it is: Wraps a specialist agent inside AgentTool(agent=…) and passes it in the parent’s tools=[…] list.
  • Why you need it: The specialist runs in an isolated sub-invocation and returns its answer back to the parent agent, which keeps control of the user chat!
6. CustomAgent (BaseAgent)
Subclass BaseAgent + _run_async_impl
  • What it is: Subclasses BaseAgent and overrides _run_async_impl(ctx) in Python.
  • Why you need it: Lets you write arbitrary imperative Python control flow (such as if/else branching on ctx.session.state) between child agents.

4. Real-world deep dive: workflow agent brain-twisters

Architect question How it works under the hood in production
“In a LoopAgent, why doesn’t the loop stop when the Critic Agent outputs the text 'APPROVED'—and how does tool_context.actions.escalate = True stop it?”
  • Deterministic event signal vs. free text: LoopAgent does not use an LLM to read its sub-agents’ text outputs!
  • Instead, after each sub-agent finishes, LoopAgent checks the emitted ADK Event.actions.escalate boolean flag. Give the Critic Agent a simple exit_loop(tool_context: ToolContext) function tool that sets tool_context.actions.escalate = True when the draft passes!
“Can we nest Workflow Agents inside each other—for example, putting a ParallelAgent and a LoopAgent inside a parent SequentialAgent?”
  • 100% composable hierarchy (BaseAgent): Because SequentialAgent, ParallelAgent, LoopAgent, and LlmAgent all inherit from BaseAgent, you can nest them arbitrarily!
  • A classic production blueprint is SequentialAgent([ParallelAgent([Credit, Fraud]), SynthesizerAgent, LoopAgent([Drafter, ComplianceCritic])]).
“When should we subclass BaseAgent (CustomAgent) instead of using SequentialAgent or LlmAgent(sub_agents=[...])?”
  • Deterministic conditional branching (if/else): SequentialAgent always runs every sub-agent in its list, while LlmAgent relies on probabilistic LLM routing.
  • If you need deterministic conditional logic—such as “Run HighRiskAuditAgent ONLY if ctx.session.state[‘loan_amount’] > 500000, otherwise skip directly to FastApprovalAgent”—subclass BaseAgent and write a standard Python if/else block inside _run_async_impl(ctx)!

Golden rules for Module 3.2

  1. Known fixed sequence = SequentialAgent. Independent concurrent lookups = ParallelAgent (with unique output_keys!).
  2. Iterative Generator-Critic cycle = LoopAgent terminated via EventActions(escalate=True) + max_iterations.
  3. Hand off the chat = sub_agents. Call a specialist and keep control in the parent = AgentTool!

3.3 MCP Toolbox for Databases and custom tool integrations

The Rosku Bank tooling crisis: database crash and SQL injection!

Rosku Bank’s developers write a custom Python function that opens a new AlloyDB database connection on every user turn and lets Gemini generate raw SQL queries to check loan balances. Within an hour of launch:

  1. 500 concurrent chat sessions exhaust all AlloyDB database connections!
  2. A clever user tricks the LLM into running a raw DROP TABLE SQL query!
  3. When the team tries to add a built-in google_search tool to the same LlmAgent that holds their custom Python tools, the agent throws a tool-conflict error!
Module 3.3 in a nutshell
  • Databases = MCP Toolbox for Databases (tools.yaml): Never open raw DB connections inside agent functions or let LLMs write raw SQL. Use MCP Toolbox (defining sources, tools, and toolsets in tools.yaml) for shared connection pooling, IAM/OAuth auth, parameterized SQL, and zero-downtime hot-reloading!
  • Custom Python tools and ToolContext: Gemini reads your function’s name, type hints, and docstring to call it. Add tool_context: ToolContext to read/write tool_context.state or set actions.escalate = True—and never document tool_context in the docstring!
  • OpenAPI, long-running jobs, and built-in tool isolation: Use OpenAPIToolset to turn REST specs into tools automatically, LongRunningFunctionTool for async jobs that return a pending ticket ID, and wrap built-in tools (google_search, BuiltInCodeExecutor) inside an AgentTool sub-agent when combining them with custom tools!

1. Key concept definitions: the ADK and MCP tooling stack

1. MCP Toolbox for Databases
tools.yaml (sources, tools, toolsets)
  • What it is: Google’s open-source MCP server connecting ADK agents to AlloyDB, Cloud SQL, Spanner, and BigQuery.
  • Why you need it: Manages connection pooling, IAM/OAuth auth, OpenTelemetry tracing, and hot-reloadable parameterized SQL in tools.yaml without redeploying agent containers.
2. Custom FunctionTool and schemas
Type hints + docstring → dict
  • What it is: Wraps a standard Python function as a callable ADK tool.
  • Why you need it: Gemini reads the function’s name, parameter type hints, and docstring to decide when and how to invoke it, expecting a structured Python dict return.
3. ToolContext (runtime injection)
tool_context: ToolContext
  • What it is: A runtime context object injected automatically by ADK into your Python tool function.
  • Why you need it: Lets your code read/write tool_context.state, load/save artifacts, or set actions.escalate = True—and is completely hidden from the LLM’s JSON schema!
4. LongRunningFunctionTool & OpenAPI
Async ticket ID & OpenAPIToolset
  • LongRunningFunctionTool: Returns an immediate pending ticket/job ID for slow async tasks without blocking the agent turn.
  • OpenAPIToolset: Parses an OpenAPI v3 spec to auto-generate callable RestApiTool operations with zero custom wrapper code.
5. Built-in tool isolation
Wrap in AgentTool(agent=…)
  • What it is: Gemini built-in tools (google_search, BuiltInCodeExecutor) cannot mix directly with custom tools on one LlmAgent.
  • Why you need it: Isolating the built-in tool inside a specialist sub-agent wrapped in AgentTool allows the root agent to use both!

4. Real-world deep dive: tools.yaml, ToolContext, and built-in tool brain-twisters

Architect question How it works under the hood in production
“What are the 3 top-level keys of tools.yaml in MCP Toolbox for Databases, and why does modifying a SQL query in tools.yaml not require redeploying our ADK agent containers?”
  • Decoupled declarative SQL (sources, tools, toolsets): In tools.yaml, sources: defines pooled DB connections, tools: defines parameterized SQL statements, and toolsets: bundles tools by role.
  • Because ADK agents dynamically fetch tool schemas from the MCP Toolbox server at runtime, updating tools.yaml on the Toolbox server hot-reloads the SQL logic with zero agent container redeployments!
“Why should we NEVER document tool_context: ToolContext inside our Python function’s docstring Args: block?”
  • Automatic schema stripping: ADK strips tool_context: ToolContext from the JSON schema sent to Gemini and injects the live ToolContext object automatically in Python.
  • If you mention tool_context in the docstring text, the LLM may get confused and attempt to invent a parameter that does not exist in its schema!
“How do we combine google_search (or BuiltInCodeExecutor) with custom FunctionTool or MCPToolset tools without triggering an API conflict?”
  • The AgentTool wrapper pattern: Gemini models cannot mix native built-in tools and custom function declarations in the same single-agent turn.
  • Create a dedicated specialist LlmAgent(name=‘search_specialist’, tools=[google_search]), wrap it in AgentTool(agent=search_specialist), and pass that AgentTool into your root agent’s tools=[…] list alongside your custom tools!

Golden rules for Module 3.3

  1. Databases = MCP Toolbox for Databases (tools.yaml) for connection pooling, IAM auth, hot-reloading, and zero SQL injection.
  2. REST APIs with Swagger/OpenAPI specs = OpenAPIToolset for zero-code RestApiTool generation.
  3. Built-in Search/Code Exec + custom tools = wrap the built-in tool agent inside AgentTool!

3.4 RAG Engine, Agent Search, and Context Caching

The Rosku Bank knowledge dilemma: 3 different knowledge needs!

Rosku Bank’s architecture team is connecting their agents on the Gemini Enterprise Agent Platform to internal bank knowledge, and they hit three distinct roadblocks:

  1. Their Employee Intranet Bot needs turnkey search across SharePoint, Google Drive, and Confluence while strictly enforcing document-level user permissions (ACLs) so junior tellers cannot see executive M&A files!
  2. Their Mortgage Underwriting Agent retrieves noisy, incomplete paragraphs from complex underwriting tables because they cannot customize the chunk size, chunk overlap, or reranking step!
  3. Their Compliance Auditor Agent sends the exact same 400-page static Basel III rulebook in the prompt on every single turn—racking up massive input token bills and 12-second latency!
Module 3.4 in a nutshell
  • Turnkey SaaS connectors + document ACLs = Agent Search: Pick Agent Search when you need rapid setup across SharePoint, Drive, Jira, or Confluence with automatic query-time document permission (ACL) filtering.
  • Custom chunking, embeddings, and reranking = RAG Engine: Pick Vertex AI RAG Engine when engineers need fine-grained control over chunk_size, chunk_overlap, similarity_top_k, vector_distance_threshold, and two-stage semantic reranking.
  • Repeatedly querying the same massive static document/video = Gemini Context Caching: Pick Gemini Context Caching (CachedContent with a configurable ttl or ADK ContextCacheConfig) when the agent needs the entire static 32k+ token document, codebase, or video in memory across many turns!

1. Key concept definitions: the grounding and context caching stack

On the Gemini Enterprise Agent Platform, Google Cloud provides four complementary mechanisms to ground agent reasoning in enterprise and live knowledge:

1. Agent Search (turnkey + ACLs)
SaaS connectors + query-time ACLs
  • What it is: The managed enterprise search engine with turnkey connectors (SharePoint, Jira, Drive, Confluence, GCS).
  • Why you need it: Provides automatic layout parsing and built-in Document-Level Access Control Lists (ACLs) enforced against the user’s identity at query time.
2. RAG Engine (custom pipeline)
chunk_size, overlap & reranker
  • What it is: The developer-controlled retrieval pipeline on Vertex AI.
  • Why you need it: Gives granular programmatic control over chunk_size, chunk_overlap, custom embedding models, vector_distance_threshold, and semantic reranking.
3. Gemini Context Caching
CachedContent & ContextCacheConfig
  • What it is: Caches a large, static prompt prefix (32k+ tokens of PDFs, videos, or codebases) in Gemini memory with a configurable ttl.
  • Why you need it: Skips re-uploading and re-tokenizing static manuals on every turn—slashing input token costs and TTFT latency!
4. Web grounding and citations
groundingMetadata & source URIs
  • What it is: Connects agents to live public facts via Google Search grounding (or Enterprise Web Grounding).
  • Why you need it: Returns groundingMetadata with verifiable source URIs and inline citation mappings for compliance auditing.

4. Real-world deep dive: retrieval troubleshooting and caching mechanics

Architect question How it works under the hood in production
“What if our RAG agent retrieves passages that cut off legal exceptions or financial tables mid-sentence?”
  • Tune chunk_size, chunk_overlap, and layout parsing: Fixed-size chunks that are too small (or have zero overlap) split semantic units apart.
  • Increase chunk_size and chunk_overlap inside ChunkingConfig (and enable layout-aware document parsing so tables and multi-paragraph rules remain intact)!
“Why does pure vector search (similarity_top_k=20) sometimes return boilerplate paragraphs that confuse the LLM—and how do we fix it?”
  • Add a two-stage semantic reranker: Dense vector embeddings measure broad semantic similarity, not exact question-answering relevance.
  • Adding a Semantic Reranker (Ranking API) re-scores the top-20 candidate chunks against the user’s exact query and passes only the top-3 highest-precision passages to Gemini (paired with a strict vector_distance_threshold)!
“When should we choose Gemini Context Caching (CachedContent) instead of chunking a document into RAG Engine?”
  • Full-document synthesis vs. needle-in-a-haystack lookup: If an agent needs to cross-reference every section of the exact same 400-page static rulebook (or a 1-hour video / large codebase) across hundreds of turns, chunked RAG will miss global cross-references.
  • Uploading the entire 400-page document into Gemini Context Caching keeps all tokens in model memory with a configurable ttl, cutting input token costs and latency!

Golden rules for Module 3.4

  1. Turnkey SaaS connectors + user ACLs = Agent Search.
  2. Custom chunk_size, chunk_overlap, and semantic reranking = RAG Engine.
  3. Repeatedly querying the SAME massive static document/video/prompt = Gemini Context Caching!

3.5 State prefixes, sessions, artifacts, and Memory Bank

The Rosku Bank memory meltdown: lost preferences and bloated state!

Rosku Bank’s Wealth and Loan Assistant has three major memory bugs in production:

  1. When a customer starts a new chat session the next day, the agent forgets their preferred language (user:language) and forgets that they mentioned saving for a house three weeks ago!
  2. Temporary calculation variables from Turn 1 leak into Turn 5 because developers didn’t scope them to a single invocation (temp:).
  3. Developers encode a customer’s 15-MB PDF tax return as a Base64 string and save it directly inside session.state, causing the database and LLM context to grind to a halt!
Module 3.5 in a nutshell
  • The 4 session.state prefixes: Use temp:key for a single-turn scratchpad (wiped after the turn ends), unprefixed key for the current session only, user:key for structured settings across all sessions of one user_id, and app:key for global config across all users!
  • Unstructured cross-session recall = Memory Bank: Call add_session_to_memory(session) so Memory Bank uses an LLM to extract, deduplicate, and semantically index long-term user facts—recalled in future sessions via PreloadMemoryTool or LoadMemoryTool.
  • Binary files = ArtifactService (never session.state!): Save PDFs, images, audio, and CSVs via context.save_artifact() into GcsArtifactService (which tracks revisions v0, v1, v2… and supports user:filename cross-session scoping).

1. Key concept definitions: the 3 storage pillars and 4 state scopes

In the Agent Development Kit (ADK) on the Gemini Enterprise Agent Platform, information management is divided across five core primitives:

1. Turn and session state
temp:key vs. unprefixed key
  • temp:key: Ephemeral scratchpad shared between sub-agents during the current single turn and wiped automatically when the turn finishes.
  • Unprefixed key: Persists across multiple turns within the current session_id only.
2. Cross-session state
user:key & app:key
  • user:key: Persists across all sessions belonging to a specific user_id (e.g., user:preferred_language).
  • app:key: Shared globally across all users and sessions of the application (requires a persistent SessionService).
3. Tracked state mutation
EventActions(state_delta=…)
  • What it is: How ADK commits state changes to the persistent session log.
  • Why you need it: Always mutate state via output_key, tool_context.state, or callback_context.state so ADK records a state_delta event—never mutate detached session objects!
4. Memory Bank (MemoryService)
add_session_to_memory & load_memory
  • What it is: Managed long-term semantic memory service on the Gemini Enterprise Agent Platform.
  • Why you need it: Uses an LLM to extract, deduplicate, and update unstructured user facts across sessions, recalled via PreloadMemoryTool or LoadMemoryTool.
5. ArtifactService (GcsArtifactService)
save_artifact & load_artifact (v0, v1…)
  • What it is: Versioned blob storage for binary types.Part payloads (PDFs, images, audio, CSVs).
  • Why you need it: Keeps megabytes of binary data out of session.state, storing them in Cloud Storage with automatic revision numbering (v0, v1…) and optional user: scoping.

4. Real-world deep dive: storage pillar sorting and state mutation mechanics

Architect question How it works under the hood in production
“When should Rosku Bank store data in session.state (user:key) vs. Memory Bank vs. ArtifactService?”
  • Structured flags vs. unstructured facts vs. binary files:
  • 1. session.state (user:tier): Known, structured key-value variables injected into prompts via {user:tier}.
  • 2. Memory Bank (MemoryService): Unstructured life events and evolving preferences mentioned casually in past conversations, extracted by an LLM and searched semantically (PreloadMemoryTool / LoadMemoryTool).
  • 3. ArtifactService (GcsArtifactService): Large binary files (15-MB PDFs, PNG charts, audio) stored as versioned Part blobs (v0, v1…) in Cloud Storage!
“Why do state changes get lost if a developer calls session = session_service.get_session() and mutates session.state['k'] = 'v' directly outside the runner?”
  • State changes must be recorded as EventActions(state_delta=…)! ADK persists state updates by appending Event objects containing actions.state_delta to the session log.
  • Always mutate state through output_key, tool_context.state[‘k’] = ‘v’, callback_context.state[‘k’] = ‘v’, or EventActions(state_delta={‘k’: ‘v’}) so the Runner tracks and commits the delta!
“How can an uploaded PDF artifact be shared across all future chat sessions for the same customer instead of just the current session?”
  • Prefix the artifact filename with user:! Just like user: state keys, calling tool_context.save_artifact(filename=‘user:w2_tax_form.pdf’, artifact=part) scopes the binary file in GcsArtifactService to the user_id across all sessions!

Golden rules for Module 3.5

  1. Single-turn scratchpad = temp: | One session = No prefix | All sessions for 1 user = user: | All users globally = app:.
  2. Unstructured cross-session semantic recall = Memory Bank.
  3. Large binary files (PDFs, images, CSVs) with versioning = ArtifactService (GcsArtifactService)!

3.6 Agent2Agent (A2A) protocol, Agent Cards, and remote streaming

The Rosku Bank partner challenge: cross-boundary agent collaboration!

Rosku Bank’s internal Mortgage Orchestrator Agent (built in Python ADK on the Gemini Enterprise Agent Platform) needs to collaborate with an external Home-Appraisal Partner Agent (built by a third-party vendor on a completely different framework and cloud). Three critical questions arise:

  1. Why shouldn’t Rosku Bank expose the partner’s multi-step appraisal agent as a simple stateless MCP tool?
  2. How does Rosku Bank’s agent dynamically discover the partner agent’s skills, endpoint URL, and authentication requirements?
  3. When a physical property appraisal takes 6 hours (or needs to pause and ask the customer for a property deed), how do the two agents stay synchronized without an HTTP timeout?
Module 3.6 in a nutshell
  • MCP (tools) vs. A2A (peer agents): Use MCP when calling a stateless function or database query; use A2A when delegating a goal to an autonomous, stateful peer agent that has its own opaque reasoning loop and internal tools!
  • Agent Card discovery and ADK helpers: Every A2A server publishes a JSON contract at /.well-known/agent.json (listing skills, capabilities, modalities, and auth). Consume remote A2A agents in ADK via RemoteA2aAgent and expose your own ADK agent via to_a2a(agent).
  • Streaming, push webhooks, and input-required: Use SSE (SendStreamingMessage) for live connected progress, Push Notification Webhooks (PushNotificationConfig) for multi-hour disconnected tasks, and reuse the exact same taskId and contextId when resuming a paused input-required task!

1. Key concept definitions: the Agent2Agent (A2A) interoperability stack

In enterprise architectures, MCP and A2A are complementary layers—review these five foundational A2A building blocks:

1. MCP (tools) vs. A2A (peers)
Function call vs. peer delegation
  • MCP: Connects an agent to a deterministic, stateless function or database query.
  • A2A: Connects peer agents across team, framework, or company boundaries where the remote agent has its own opaque reasoning loop and state.
2. A2A Agent Card
/.well-known/agent.json
  • What it is: The machine-readable JSON contract published by every A2A server (and indexed in Agent Registry).
  • Why you need it: Declares the agent’s skills, capabilities (streaming, pushNotifications), input/output modalities, and auth schemes without exposing private prompts or code.
3. Task lifecycle and SSE streaming
taskId + contextId & SSE
  • What it is: Tracks stateful work units across submitted → working → completed.
  • Why you need it: When capabilities.streaming=true, streams live TaskStatusUpdateEvent and TaskArtifactUpdateEvent messages over SSE.
4. Push webhooks and input-required
PushNotificationConfig & pause
  • Push webhooks: For multi-hour disconnected tasks, the server POSTs updates to a callback webhook URL.
  • input-required: If the remote agent needs missing user data mid-task, it pauses in state input-required until the client replies with the same taskId.
5. ADK RemoteA2aAgent & to_a2a()
Client wrapper & server publisher
  • RemoteA2aAgent: Wraps an external A2A endpoint so an ADK coordinator can delegate to it like a local sub-agent.
  • to_a2a(agent): Exposes your existing ADK agent as an A2A-compliant server!

5. Real-world deep dive: A2A Task resumption and streaming mechanics

Architect question How it works under the hood in production
“When a remote A2A agent pauses in state input-required (because it needs the customer’s parcel zoning number), how does the Client Agent know what question to ask and how to resume?”
  • Status message + reusing taskId and contextId: When transitioning to input-required, the Remote Agent attaches a Message (containing a TextPart or structured DataPart explaining what field is missing) inside the TaskStatus.
  • The Client Agent obtains that info (from its own state or by prompting the human user) and sends a follow-up SendMessage carrying the exact same taskId and contextId so the Remote Agent continues right where it paused!
“What is the difference between an A2A Message and an A2A Artifact?”
  • Conversation turn vs. task deliverable: A Message represents conversational dialogue, instructions, clarifications, or status thoughts exchanged between the Client Agent and Remote Agent.
  • An Artifact represents the formal output deliverable produced by the Task (such as a generated PDF appraisal certificate, a compiled code file, or a final structured JSON report) streamed via TaskArtifactUpdateEvent.
“When should we use SSE (SendStreamingMessage) vs. Push Notification Webhooks (PushNotificationConfig)?”
  • Connected seconds/minutes vs. disconnected hours/days: Use SSE (message/stream) when a user or orchestrator is actively connected and waiting for real-time progress updates over seconds or a couple of minutes.
  • Use Push Notification Webhooks when a task takes hours or days (like physical inspections or batch settlements) so neither agent has to hold an open HTTP socket!

Golden rules for Module 3.6

  1. Deterministic function / database query = MCP | Autonomous stateful peer agent = A2A.
  2. Real-time connected progress = SSE (SendStreamingMessage) | Multi-hour disconnected jobs = A2A Push Notification Webhooks.
  3. Remote agent needs more info mid-task = input-required state (reply using the exact same taskId!).
